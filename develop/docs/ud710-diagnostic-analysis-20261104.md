# UD710 实际诊断：发送排队与接收积压

分析用户提供的 `66b11c9a-afdf-4da3-9944-8c2d8fa5cbcb.tar.zst`，原始内容与复算脚本仅保存在忽略目录 `develop/tmp/ud710-66b11c9a/`。收集34.90秒，33个Client、18个Control和18个Endpoint记录；手动停止，无来源缺失或截断。客户端为Brave/Chromium138、Android10，视频1936×816。浏览器暴露的硬件线程数和内存是能力提示，不能直接当作物理设备配置。

## 结论

早段存在实测的秒级Endpoint发送队列等待；队列清空后，客户端又出现末包到齐后数百毫秒的等待。之前只优先怀疑接收端的判断不完整。当前最强线索是低活动后的低发送预算、编码输出突发及其后的播放积压。该包不支持“低RTT所以网络一定正常”，也不支持把主要秒级延迟归因于纯解码运算。

## 分段证据

阶段位置按Control收集时间标识；各统计差分在各自源时钟中计算。

| --- | --- | --- |
| 前约6秒发送队列 | 包加权平均1149ms；单秒窗口1276–1773ms | 明确的发送前排队，不能解释成平板解码时间 |
| 前段同RTP时序 | 元数据经DataChannel到达后，视频末包还需约1.42–2.01秒；末包到提交12–21ms | 与发送排队相互印证；元数据到达不是视频发包时刻，不能据此计算单向网络耗时 |

在当前Endpoint使用的Chromium157源码中，`prioritized_packet_queue.cc`记录非暂停的包排队时间，经`rtp_rtcp_defines.cc`累计后由`rtc_stats_collector.cc`导出`totalPacketSendDelay`。这比早先保守称为“发送前等待”更精确。发送`framesSent`在该版本来自编码帧计数，不能当每个完整帧已发出；真实发包证据使用packetsSent/bytesSent。

## 可定位的适配问题与待验证因素

1. [SDK](../../browser/sdk/remotekit_rtc.cc)声明`has_trusted_rate_controller=true`。固定WebRTC的`api/video_codecs/video_encoder.h`要求可信控制器快速跟踪目标并控制超发；`video/video_stream_encoder.cc`据此关闭常规单层编码前丢帧保护。现场约0.06–2.12秒的编码产出1.55Mbps，窗口两端分配约0.517→0.633Mbps，发送队列约1493ms/包；约22.3–24.3秒编码产出22.04Mbps，窗口两端分配约5.74→6.47Mbps。缺少窗内完整分配曲线，但与“快速可靠跟踪”的假设存在明显矛盾。优先做仅改变该声明的受控对照，保留WebRTC作为拥塞控制主体。
2. QSV默认VBR，现场最大码率保持48Mbps。SDK传给硬件的`gccTargetFps`实际含WebRTC观测输入帧率，不是独立的GCC帧率上限。[QSV SetRates](../../endpoint/src/media/qsv_encoder.cpp)在整数FPS变化时启动新序列并请求IDR。全程新增85个关键帧、159次参数应用，idle尾IDR只新增7次，SDK显式关键帧请求无增量。频繁FPS变化有机制放大关键帧突发，但尚缺逐次Reset/重建和IDR原因，不能把85个全部归因于该路径。参数应用计数也包含子kbps空操作。
3. 本地WebRTC screenshare默认策略包含约2875ms队列时限、1.0 pacing factor和周期ALR probing；当前已经默认启用探测，不能把“开启ALR”当成新增修复。包内未记录实际探测事件及实时pacer队列深度，当前不修改原生拥塞阈值。
4. 音频左右声道均关闭，但这只是播放增益；实际仍接收Opus。音频实际/目标/最低缓冲为142.9/177.3/177.3ms，新增12次concealment、70290个补偿样本；SDK增加631个10ms静音块和11次gap restart。音视频同属`remotekit`同步组，可能影响视频播放，贡献需对照验证，不能把目标相近视为因果证明。

原生编码队列727次均值16.2ms，多数最近编码耗时8–18.4ms，单次采到44.3ms；硬件busy/队列满/编码错误均为0。Control约2秒采样稳定，Browser/RTC/output始终可用。约26–28秒新增标签与输出代次2→3对应，非前段秒级积压的原因。

成功输入回执与发送序号在Viewer同一时钟关联：406个惯性滚动事件中位40.1ms、p95 147.5ms；182个触摸事件35.8/107.4ms。这是应用回执往返，不是input-to-present，未采到的序号不当成丢失。
