# UD710 后续：RTP playout 上限筛查

状态：已完成串行50→10的两组70秒真实运行。10ms虽降低末包→提交等待，却使提交FPS降低15–17%，页面marker尾延迟未改善；root决定拒绝10ms，默认继续50ms。未做反序、未测30ms，不能由本组推断所有更小值均无效。

同一 Endpoint/SDK、Control 产物与 Chromium157 Viewer，audio-on、VBR、CRC16 与 VideoFrame 时间戳核对，固定 1936×816 atlas、下行24Mbps、基础单向5ms。沿用30秒静止→22秒滚动→5秒静止→13秒滚动。只通过既有 `--rtc-playout-max-ms` 比较50与10，先50后10；不新增产品开关，不用0。实际 SDK/Endpoint/Viewer chrome.dll、运行依赖和Control资产hash随 plan 保存，每组前复核。

本地 Chromium157 `video_receive_stream2.cc::UpdatePlayoutDelays` 会将包含音频同步在内的minimum限制至收到的maximum；min=0/max>0另按60FPS换算composition队列预算，50与10分别约3与1帧。实际minimum为正时不走立即呈现。max=0有不同的composition metadata/解码节拍语义，因此不属于本组。max不是对实际接收等待的严格时限，不能把50ms请求解释为全部缓冲≤50ms。

运行归档必须验证Endpoint请求min=0/max=所选值、Viewer收到相同请求信息、RTP扩展已协商与jitterBufferTarget读回0。该读回证明请求/协商链路，不是逐包RTP扩展抓包或接收器内部最终minimum读回。音频必须仍有双方RTP包/字节。

比较两段运动的发送队列、实际/target/min缓冲、组帧、解码、CRC marker、提交FPS、RAF、掉帧、冻结及RTT。只有接收或页面到提交改善超过15%、且无明显FPS/发送负载/质量混杂，才反序10→50确认；否则停止。本fixture发送静音Opus，不能证明真实音频听感或口型同步；10ms若仍超过100ms缓冲，不继续压低，交由接收器trace调查。

证据目录：`develop/tmp/ud710-playout/`。工具：`tools/ud710-playout-scenario.mjs`，复用既有诊断运行器与分析器。无上传、构建、提交。

## FPS、丢帧与冻结的计数范围

compositor FPS来自rVFC `presentedFrames` 首尾增量/阶段时长，回调数单列，二者不互换。两组首段/第二段RTC `framesDecoded` 增量分别1174/687与1161/687，`framesReceived`增量相同，`framesDropped`增量全部0。这只说明接收/解码端没有计入该类掉帧，不能据此否定之后的呈现丢弃。当前归档没有选中view的element播放质量计数，因此不虚构element drop数。

rVFC间隔最大值首段/第二段为50ms组187.9/166.7ms、10ms组205.8/168.6ms。首段freeze计数增量50为0、10为1（186ms）；第二段两组均1，累计时长增量4795/4799ms。这约4.8秒包含前一人为5秒静止段，在恢复时入账，不能当成第二段持续滚动的额外4.8秒卡顿。其余阶段边界也保留在原始归档，未选择性删去恢复尾巴。
