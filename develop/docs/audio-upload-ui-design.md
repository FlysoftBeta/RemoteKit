# Viewer 音频与文件选择 UI 建议

2026-11-02；设计建议，未实现、未构建、未做浏览器或摄像头验证。最终状态归属与接口由 root 确定。

## 对照现有实现的结论

- `control/client/main.tsx` 的 `Workspace` 已持有一个 `RemoteTransport`、Control 状态和全局 dialog。音频播放与文件选择 dialog 应在此层挂载一次；每个 `WindowFrame` 的更多菜单只是入口。
- `window-frame.tsx` 的更多菜单已有站点设置、设置与账号区。音频组放在“使用平板版网站”之后、“设置”之前，沿用菜单浅底和留白，不新增工具栏。
- `product-dialogs.tsx` 已有 MUI `Dialog`、600px 窄屏全屏设置、页面对话的来源信息。文件选择沿用这些视觉惯例，但拆为独立组件，避免继续扩大该文件。
- `shared/product.ts` 的 `ProductSettings` 和 `settings.update`、`server/store.ts` 的设置合并/持久化路径可容纳音频偏好。文件选择是有生命周期的页面请求，不是持久化设置。
- 当前 `PageDialogs` 与其他 dialogs 分别挂载。新增文件 dialog 时需要统一确定当前前台 modal，避免两个焦点陷阱叠加；这不要求重写全部 dialog。

## 1. 音频：更多菜单里的一个紧凑组

建议常态一行：

```text
声音   左声道 [开]   右声道 [开]   不播放
```

“左声道”“右声道”分别为 MUI `Switch size="small"`，标签与开关整体可点击；“不播放”为文字按钮。默认左右均开，点击“不播放”原子地清空两者；两者都关时该按钮显示选中底色，语义仍是“清空”，再次点击不会恢复旧偏好。无需第三个互斥开关、总音量、保存按钮或独立音频设置页。

组使用 `role="group" aria-label="整个工作空间的声音"`；可用短标题“声音”，范围通过无障碍名称及标题 tooltip 说明。视觉宽度目标约 340–360px；菜单最大宽度继续受视口约束。390px 可优先整行，320px 或放大字体时允许“不播放”换到第二行；不得为保持一行缩小触摸目标或隐藏声道全称。控件行最小高度 44px，无外框，不需要在组内加竖线。

不要把两个 Switch 和按钮嵌入同一个可点击 `MenuItem`：这会混合菜单项和表单焦点行为。建议更多弹层采用 `Popover`，普通操作用 `MenuList` 分段，音频组作为菜单列表的兄弟 `Box`；保留普通菜单项的方向键操作，音频组使用 Tab/Shift+Tab 和 Space。若保留现有 `Menu`，实现者必须明确处理该组的焦点进入/退出，不能只靠 `stopPropagation`。音频切换后弹层保持打开。

### 保存与播放状态

- 建议持久化两个布尔值（例如 `audioLeftEnabled`、`audioRightEnabled`），避免另存一个会矛盾的 `muted`。该命名仅为建议。
- 保存为完整声道对，以同一个 `settings.update` 原子发送。保存期间禁用本组，显示短暂 `aria-live="polite"` 状态；成功不弹 toast，失败在组下显示“声音设置未保存，请重试”。错误仍在时应可再次操作。
- 所有 Window 显示同一份 Control 状态，播放只应用一次。新标签页、切窗口、窗口聚焦不能重置偏好；刷新从 Control 恢复，客户端不写 localStorage/IndexedDB。
- 可以短暂乐观显示和应用音量门控，但失败必须回到服务端已确认值；本组不允许并发保存导致旧回复覆盖新值。若不做乐观更新，等待期间也不得把开关误画成已保存。
- 输出声道选择保持立体声位置：关左仅静音左输出，关右仅静音右输出，不将剩余声道复制到两边。单声道如何映射由媒体契约定义，建议先正常上混再按输出声道静音。
- 浏览器阻止播放是临时本机状态，不能把已保存的开关自动关掉。偏好至少开启一个声道且播放被阻止时，组下出现“点击开启声音”按钮；同一动作可在页面上方显示一次小型覆盖提示，避免用户必须先找菜单。提示不占布局、不改变内容区尺寸、不自动消失；恢复成功即消失。全部关闭时不提示。
- 用户点击开启声道、更多中的恢复按钮或覆盖提示时，直接在该手势内尝试恢复播放；不要等待设置网络请求完成才调用恢复。仅在得到明确播放成功/失败状态后更新提示，不把点击当成成功。

## 2. 文件选择：一次 dialog，先本地选择，再确认

独立 `FileChooserDialog` 挂在 `Workspace`，由正在展示的有效请求驱动。标题“选择文件”；标题下显示请求网页的来源（如 `https://example.com`），长来源可换行，不能仅展示当前地址栏来冒充请求来源。

初始布局：

```text
选择文件                                      ×
https://example.com

[ 从设备选择 ]   [ 摄像头拍照 ]

                               取消    使用文件
```

仅两个来源按钮，不做大卡片、向导步骤或永久 tabs。尚未选文件时“使用文件”禁用。设备文件选择器关闭/取消后返回该 dialog，不自动取消整个网页请求。选择后展示紧凑文件列表：文件名、大小、移除按钮；设备图片可有小缩略图，非图片使用普通文件图标。不对任意文件创建大预览。

“从设备选择”触发普通 file input，传入网页的 accept/multiple，明确不设置 `capture`。选择文件只放入当前 dialog 的内存草稿，确认前不向服务端传文件内容。重复选文件在多选请求中追加并防止同一文件被误重复选入；单选请求替换当前草稿。清除 input 的 value 后允许再次选同一文件。

仅当请求允许一种受支持的照片格式时启用“摄像头拍照”；例如网页只接受 PDF，就在该按钮附近显示“此页面仅接受 PDF 文件”，而不是让用户拍完才失败。具体格式、文件数量、单个/总大小以服务端下发限制为准。普通 accept 应同时传给系统选择器并在确认前验证，扩展名/MIME 检查不能代替服务端校验。

### 摄像头流程

1. 点击“摄像头拍照”才调用 `getUserMedia({ audio: false, video: ... })`，进入预览。标题不变；来源按钮区域替换为预览与“拍照”“关闭摄像头”。首次等待显示“正在打开摄像头…”；用户可随时关闭/取消。
2. 默认请求后置摄像头作为 preference，失败不必因无后置而拒绝其他摄像头。只有确有多个可切换摄像头时显示一个带文字/无障碍名称的“切换摄像头”图标按钮，不增加设备设置页。切换先停止旧轨道。
3. 按“拍照”采集一次短序列，短暂显示“正在选取照片…”，禁止重复拍摄。建议初始预算：约 600ms 内最多 6 帧，用最长边约 160px 的小图评估清晰度，最多保留 3 张候选；候选顺序按拍摄时间，减少用户辨认负担。不得持续逐帧打分或无限缓存；这些数值是内部初值，非 UI 调参项。
4. 完成这一批后立即停止摄像头，展示候选。选取规则仅是清晰度启发式，不能向用户保证“最佳”或“清晰”；低光/运动时仍让用户判断，不因评分低阻止上传。
5. 候选无默认勾选。用户点选照片；单文件请求使用单选，多文件请求可选若干。缩略图角落显示勾选标记，选中态使用轻底色/一圈强调色，不仅靠颜色。提供“重新拍照”与“从设备选择”，前者显式重开摄像头并替换本批候选，不无限追加未选候选。
6. 保留原始比例，预览 `object-fit: contain`；前置预览如采用镜像，交付照片仍需明确一致的方向规则，避免拍文字得到镜像成品。候选图可以点击单独的“查看照片”按钮在 dialog 内放大，返回保留选择，不叠第二个 modal。
7. 页脚“使用文件”或“使用 2 个文件”才开始传输与提交。拍照、点击缩略图、关闭摄像头均不提交。

建议预览请求上限初值约 1280×720、15fps；采样计算降采样，逐个处理帧，最终候选按网页允许格式编码。只有候选保留 Blob/object URL，其余立即释放。不用 ImageCapture、OffscreenCanvas 或特定新 API 作为唯一实现前提，避免排除 Chrome89；能力增强可后续单独做。采样期间不能抢占 Viewer 的连续渲染循环。

### 窄屏与触控

- 桌面为 `Dialog fullWidth maxWidth="sm"`，建议最大 600px 左右；600px 以下全屏，标题与页脚保持可达，中间内容滚动，底部尊重安全区。
- 预览高度限定为可用高度的一部分，横屏/软键盘变化时可收缩，不能把“拍照”与“取消”推到不可见位置。候选为 2–3 列自适应网格，390px 推荐 3 张并排，允许放大查看。
- 所有图标/拍摄/选择热区至少 44×44px；不依赖 hover、长按、双击或左右滑动。照片选择点击整张卡片，查看使用独立按钮，避免一次点击含糊地既选择又放大。
- dialog 是覆盖层，不改 `WindowFrame` 内容区尺寸；开启、拍照、选择和确认都不得触发远端 viewport 缩放。

## 3. 状态流、取消和错误

建议本地状态保持简单：`choose → camera-opening → camera-preview → capturing → review → submitting`，另有可恢复错误。设备文件可从 `choose` 直接到 `review`；相机失败退回可继续设备选择的页面。状态命名不属于最终协议。

| 事件 | UI 与资源行为 |
|---|---|
| 取消、×、Escape、点遮罩（提交前） | 同一个 cancel 流程：停止所有轨道、释放采样与预览、取消网页请求，不上传草稿 |
| 打开相机过程中取消 | 请求序号失效；权限稍后成功返回的 stream 也立即 stop，不让迟到结果重新打开 dialog |
| Viewer 隐藏/失焦到其他应用 | 页面变为 hidden 时停相机和采样；回到页面只显示“继续拍照”，不自动重开。普通窗口 blur 不等同 hidden，系统权限/文件选择器可能导致 blur |
| tab 导航/关闭、请求失效、Endpoint 换代、租约撤销/注销 | 停止相机，清空草稿并关闭；不得把旧照片提交给新页面。可在外层显示“页面已更改，文件选择已取消” |
| 暂时断线 | 停相机，禁用提交；恢复后仅在同一请求仍有效时允许继续，不自动恢复上传或摄像头 |
| 提交中 | 页脚显示“正在发送…”与进度（有可靠总字节时）；禁用重复确认和更换来源。保留显式“取消发送”，须由后端提供可取消上传/草稿清理语义；不能只是把 dialog 隐藏 |
| 取消与最终提交竞态 | 后端确认提交完成后显示结果并关闭；不能已经提交后仍宣称“已取消”。提交完成后页面如何上传文件由网页自身决定 |
| 传输失败 | 停止发送，保留当前内存选择，显示“文件未发送，请重试”；重试需再次点击，必须确认请求仍有效 |

权限拒绝用“无法使用摄像头，请允许访问，或从设备选择文件”；无设备用“未找到摄像头”；非安全上下文用“当前连接无法使用摄像头，请使用 HTTPS，或从设备选择文件”。错误靠近来源/预览位置，使用一个简短 Alert，不展示异常堆栈、评分、帧率与硬件参数。

系统文件选择和浏览器摄像头权限 UI 都可能暂时把焦点移出网页；不要因此判定用户取消。取消请求采用显式操作/有效生命周期事件，迟到异步结果统一通过请求标识与本地 generation 过滤。

## 4. 最小接口需求与整合点

以下只是 UI 所需信息，不替 root 确定协议或上传通道：

- 音频：Control 返回持久化声道偏好；播放器另提供本机 `playing / blocked / unavailable` 等最小可观察状态与用户手势恢复方法。没有音轨不等于 autoplay blocked。
- 文件请求：不透明 `id`、`tabId/windowId`、可信显示来源、`multiple`、规范化的接受格式/显示提示、可支持模式和数量/体积限制。客户端不可持有或构造服务端文件系统路径；绑定页面身份与文档有效性由服务端负责。
- 文件操作：cancel、用户确认后开始发送、进度/取消、最后一次提交结果；客户端草稿文件不能混入 ProductState 或持久化设置。
- 前台请求选择：与 `PageDialogs` 共用当前可见 tab 判定，多个窗口同时请求只显示一个，优先活跃窗口后按稳定顺序处理。后台 tab 保留待处理标记，不自动切页；本批将现有 tab 标题中的页面对话圆点扩展到文件请求即可。
- 当前 dialog 打开期间，所有全局快捷键（尤其 `WindowFrame` document capture 的 Ctrl/Cmd+L）都必须尊重 modal 状态；不能把键盘、文字输入或触摸泄漏到远端页面。关闭后恢复原触发区域/页面输入焦点，目标已不存在则回到当前窗口安全焦点。
- MUI dialog 设置 `aria-labelledby` / `aria-describedby`；候选使用 checkbox/radio 原生语义与可读名称，如“照片 2”；开始/完成、选择数量与失败通过 polite live region 宣布，不逐帧播报。提交错误保留可键盘到达的重试和取消。

## 5. 必要验收（不扩成性能矩阵）

1. 左右四种组合、清空、保存失败、刷新/另一个窗口同步；autoplay 阻止与手势恢复不改变保存偏好。
2. 单选/多选、accept 不支持照片、设备选择取消、再次选择同名文件；确认前无文件内容发送。
3. 真摄像头权限允许/拒绝、短序列候选、选中确认、重新拍照、导航/断线/隐藏时 stop，尤其迟到 `getUserMedia` 结果的清理。
4. 取消上传与完成竞态、旧请求不能提交、重试不重复交付；这些结果以实际上传链路验证，不能只测组件。
5. 390px、320px、大字体、桌面并排窗口；音频组可操作、页脚可见、开关/弹窗不改变远端内容尺寸。Chrome89 的基础 camera/canvas 路径与键盘焦点至少做一次功能检查。

视觉验证按仓库约定由 Sol6.1 执行。本设计文件不构成上述检查已经通过的证据。
