# 调优经验

这里集中记录性能与正确性调优中得到的结论，包括被否决的方案和否决理由。各子系统的现行设计见对应文档；这里讲"为什么不是别的样子"。

## 目标与环境

参考环境是 Intel UHD630（QSV）、RTT 10ms、每 peer 24–48Mbps 的整形链路。目标：动态 canvas 实际 ≥50FPS、Pixel marker p95 ≤100ms；静态页面低 FPS 是正常的。重载目标是 2–3 个租户同时活跃。

在旧的捕获路径上曾达到双租户 45 秒同组约 51.7FPS、marker p95 76/79ms（1920×1080/DPR1、atlas 1936×1088、48Mbps、headless 接收端）。这组数字属于旧架构（CopyOutput 捕获 + Canvas 接收），不能当作当前 OSR + video 路径的结果。当前路径在 24Mbps 带音频的条件下提交约 46–47FPS，接收端等待仍是 100ms 目标的主要差距。

## 渲染路径

**问题不在拷贝，而在完成观察和 Present。** 旧路径（子 CopyOutput 捕获 → Browser 源纹理 → Browser atlas Slot → Endpoint 私有纹理 → VPP/编码）在 4 租户 50FPS 时理论上有约 10GB/s 的拷贝流量。但 profile 显示：子渲染约 1.5ms、根约 1.0ms、拷贝约 1.0ms，而 CPU 侧等待完成约 100–120ms；CopyOutput 请求→完成中位数约 200ms，GPU 批次只有约 0.8ms。官方的完成回调经常在等 `CommandBufferStub::PerformWork`；一个 137ms 的作用域里 DXGI Present 墙钟 132ms、CPU 只有 0.47ms。提高同一线程的优先级无法抢占它自己阻塞的 Present；关闭 DirectComposition 只是把延迟挪到约 448ms 的 PostSubBuffer。ETW 中源 DMA 包排队 125–225ms，执行只要 2.7–4.3ms。

结论：与其在隐藏 swapchain 的阻塞行为周围做调度，不如把服务端 OS 呈现从路径中移除。这就是当前的直接 OSR 输出设备（[渲染](rendering.md)）。

沿途的局部优化各有收益但都没有解决饱和问题：单 plane 直接发布去掉 Browser 中间拷贝（源 16FPS 时 p95 130–197→90–149ms，3D 88%→80%，但源 30FPS 时客户端仍约 7FPS）；DPR1 根捕获把一个子 pass + 根 pass 合成一个 pass；Endpoint 直接共享 atlas 输入去掉私有拷贝（固定源 52 时 40.2/40.5→46.9/48.3FPS，p95 128/126→83/94ms）。教训：去掉一处浪费不等于消除下游饱和；Slot 去掉拷贝时必须保留逐 Slot 的内容基线，否则部分更新会留下旧区域。

**宿主缩放**：服务器桌面 150% 缩放时，DPR1 的页面被渲染成 2880×1620 再捕获成 1920×1080。修正后 4 租户源吞吐约 8→20FPS，而客户端只从约 6.5 升到 9.3FPS；另一次宿主缩放实验源 20→25FPS，客户端反而从 8.3 降到 6.7–7.5FPS。这正是"服务关键参数要独立于宿主显示设置"的来源：现在服务进程使用虚拟 Screen（DSF=1），页面 DPR 显式指定。

## 节奏

- **源帧率不是目标。** 4 租户源 60FPS 时客户端约 4.85–6FPS、p95 1.66–2.11 秒、3D 99.8%；源约 16FPS 时同类负载客户端约 15.2–15.9FPS、p95 184–317ms。准确的需求比激进的生产更好。
- **定时器**：Browser `RepeatingTimer` 配置 60/30/20 只跑出约 34/22.5/16（量化）；改成绝对期限后得到 59.98/30.02/19.98——但正确的定时只是暴露出真实的 GPU 容量，并没有增加容量（准确的 20FPS 需求把 3D 推到 99.6%，客户端约 10FPS）。
- **周期轮询会制造第二个节拍**：用"now − last ≥ interval"做发布，55FPS 的源只发布出 42FPS，125 次回调被覆盖；改成绝对期限加脏标记唤醒后发布约 54.95FPS。测试页也犯过同样的错（rAF 60 而渲染只有约 54.9）。
- **有界队列是安全属性，不是吞吐保证**：捕获容量 1 和 2 都没能修复后来的负载问题（约 1.6/3.2FPS）。
- **自适应控制器的教训**（旧的源预算控制器，现已删除）：把容量反馈和产品偏好分开；要求新鲜的反馈、迟滞和有界恢复；绝不让观测到的源饥饿变成它自己的永久速率上限。
- **先计数再加深度**：在源到交付之间丢帧时，先给每个接纳原因和每个归还边界计数（damage、oracle 拒绝、全部 Slot 忙、捕获结果、发布、借出、最后读者、consumed 观察、Done、归还），再考虑增加 Slot。曾经 `heldSlots` 只统计有正引用的已借出 Slot，不含进行中的捕获和归还路径，均值 1.11 看起来很空，其实三槽池经常被占满。

## 编码

被否决的 QSV 方案（都在 UHD630 上与当前方案串行对照，都已从产品代码中删除，不保留开关）：

| 方案 | 结果 | 否决理由 |
|---|---|---|
| 固定 60FPS 名义时基 | 2Hz 内容停稳 MAE 2.33→5.14，15Hz 2.02→2.42；稀疏页码率约 2.88→0.30Mbps | 码控按名义帧率分配每秒预算，虚高的时基让稀疏更新饿死；发送队列变短只是因为输出变少 |
| 仅 BRC 提示实际帧率（约 3FPS） | 2Hz MAE 4.84 | 画质仍明显退化 |
| `LowDelayBRC=ON` | 2Hz MAE 2.40→20.3，15Hz 2.01→19.4；码率 2.55/9.09→0.19/0.45Mbps | 发送等待降到约 0.1ms 的代价是严重的画质损失。现在请求 UNKNOWN，读回 OFF |
| 动态 I/P 帧预算（T=码率/(8×名义FPS)，I=5T、P=2T） | 驱动接受；15Hz MAE 2.01→3.46、RMSE 3.88→5.41，2Hz 几乎不变 | 15Hz 的稀疏内容退化是决定性的。另：固定 I150KB/P100KB 在 60FPS 被接受，2FPS 时被驱动清零（status 5）——驱动接受不等于生效 |
| 同 session 异步 VPP | 见[编码](encoding.md#转换vpp) | 把工作挪到已饱和的 3D 引擎 |

保留的组合：时基去抖 + 不可信码控（恢复 WebRTC 超发保护）+ 原生 screenshare pacing 1.1。去抖版本的停稳画质恢复到 2Hz MAE 约 2.56、15Hz 约 2.01。

其他：
- 一个 300KB 的 AU 在 24Mbps 上仅串行化就要约 100ms，所以关键帧突发的大小很重要，即使 Reset 本身很快。
- 旧的 LowPower/TU 对比：4 租户下打开 QSV LowPower 让 Endpoint 3D 约 21%→15%，但总 3D 仍在 99.8% 附近，客户端没有改善。TU7/LowPower ON 是当前默认，但不保证在任何饱和的多租户负载下都更好。
- 历史上同一负载下 CBR/VBR 的静态 MAE 8.81/8.48、PSNR 23.46/23.50，VBR 只用了约 2.5–4.1Mbps 而 CBR 用了 16–18Mbps。这是负载相关的结果，不是普遍等价。

## 网络与接收

- 真实移动设备（UD710/Brave138，RTT 约 15ms）的一次 34.9 秒诊断里，前段发送包排队均值约 1.15 秒（窗口约 1.3–1.8 秒），而此时接收→合成只有 12–21ms；后段 jitter buffer 停留升到约 346–935ms，末包→合成约 314–944ms。平均纯解码约 12.6ms。瓶颈在不同阶段之间移动，秒级延迟不能归因于解码。整段丢包为 0 但 RTX 165 个（0.67% 包）。这次诊断直接导致了"不可信码控"和"时基去抖"两项修复。
- 音频隔离：一组有/无音频对比中首/次运动段接收等待 270/89ms vs 44/44ms；反序、不读回像素的一组为 50/60 vs 44/48ms，没有稳定复现，不能认定音频是唯一原因。这些组的 Viewer rAF 都在 32Hz 附近，与 rAF 约 53Hz 的组不能直接比较。
- 接收端 playout：0/50 保留，0/10 否决，见[呈现](presentation.md#接收端缓冲)。发送 pacing：1.1 保留，1.5 否决，见[编码](encoding.md#发送节奏)。
- 同机的 UDP 中继网络模拟本身是负载的一部分（高负载时约 1 核）；`setTimeout` 轮询（约 5ms）会把名义 10ms RTT 推到 31.8ms，改用 `setImmediate` 后 p50 10.2ms。Chromium157 的 P2P 拦截器在 socket 创建前安装全局规则即可整形真实 RTC（早先"CDP 不影响 RTC"的说法不成立）：48→4→48Mbps 时 GCC 目标约 33→0.79→3.5Mbps（10 秒后），解码持续，但没有观察到网络驱动的尺寸变化，也没有完全恢复到原目标。

## 客户端呈现（历史）

当前只有 video 后端。之前依次尝试过：MSTP（MediaStreamTrackProcessor）+ Canvas、双帧 FIFO、共享 WebGL 绘制。

- FIFO2（溢出丢最旧、每 rAF 消费一帧）：46.5/46.1FPS、p95 91/89ms → 49.6/50.0FPS、94/103ms，被替换帧 233/255→46/42。它接近但不保证 50FPS，用一点停留时间换来更少的错失机会。
- 共享 WebGL（单个 atlas 纹理、按 viewport/scissor 绘制各平面）：4 平面 CPU 1.22→0.42 核等价，3D 25.9%→10.6%，绘制 p95 4.3→0.9ms。
- `alpha:false` 的不透明 canvas 没有改善（45.7/46.9FPS vs 46.9/48.3FPS）。调整 rVFC 请求顺序约 47.35 vs 47.04FPS，没有稳定收益。连续 rVFC 实验（patch）51.2 vs 52.8FPS、p95 104 vs 123ms，没有同时改善吞吐和延迟，已删除。
- 输入门禁的教训：每次读帧都调用 `frameGate.observe` 会让同一 epoch 内已绘制像素的资格失效；"观察到的""被接纳的""实际绘制的"身份必须分开。
- 在固定源 50 下 Canvas 约 49.8FPS，video 合成约 47.6FPS、rVFC 约 43.5FPS——三者测的是不同终点。video 相关 3D 更低不能说明回调吞吐更高。改为 video-only 的决定不能用合成计数替换旧的应用绘制计数来论证；它的理由是去掉一整套 JS 帧管理、与浏览器原生解码合成路径对齐，以及删除后端切换带来的状态复杂度。
- 旧的 headless 接收端的 Chrome89 曾因没有 DXGI 输出而退回 `Sleep(17)` 的假 vsync，空页面上也累积约 31ms。headless 不等于软件光栅或软件解码（实测仍用硬件 ANGLE/D3D11）。

## 输入

- 触控用到达时间喂给速度跟踪会丢失或放大惯性 → 源时钟贯通 + 客户端计算完整惯性，见[输入](input.md)。
- 整个触摸转滚轮被否决（破坏 touch-action 等）；把客户端速度交给原生 FlingController 被否决（仍依赖到达时间）；服务端渲染器的滚动重采样被关闭（与客户端位移叠加）。
- 无屏幕的 Windows 物理指标返回 PPI 0，导致原生 fling 曲线被禁用 。当时用补丁固定了 96 逻辑 PPI；改为客户端计算完整惯性后，原生 fling 不再参与，该补丁随服务端识别路径一起删除。
- 输入链路各阶段（客户端 DC 发送→Endpoint p95 13.2ms、Endpoint 排队 1.5ms、工作线程 3.3ms、RPC 锁 0.004ms、Browser 派发 0.3ms、处理 2.0ms）都不大；首次交互的焦点 ACK 约 27ms 是真实成本。
- 输入回执测的是应用往返、受理和终止行为，不是"输入到可见响应"。后者用 marker 测。

## Viewer 主线程

低性能平板（1280×800 触屏、DPR 2、CPU 6× 节流）上的瓶颈是 React/MUI 的重复协调，而不是解码、布局或绘制：三窗口串流时主线程约 82% 是 React 根的工作，脚本 928ms/s，布局与绘制几乎为 0。来源与对策：

- **视口与快照的反馈环**：空闲时快照只有 `snapshotSequence` 不同，12 秒内 79 次视口请求产生 168 个快照。现在视口按规范化 JSON 去重，服务端只在内容变化时推送，客户端收到相同内容不替换快照对象。空闲主线程 486→89ms/s。
- **整个舞台订阅整个会话**：每个呈现、统计、RTC 变化都重渲舞台。现在 `useViewerSessionSelector` 只订阅选择器实际读到的源，并按值缓存选择结果；`PresentationSession` 只在界面会读到的内容（阶段、布局、错误、各视图就绪）变化时发布，逐帧的 RTP 不进快照；统计只由显示它的组件订阅。三窗口动画 rAF p95 186→20ms。
- **我的文件**：无关更新重建全部已挂载的 MUI 行（约 97% 主线程）。上下文值与窗口 state 在内容不变时保持同一对象，行与卡片 memo 化、回调按 ID 稳定，列表虚拟化。列表帧 p95 695→37ms，PDF 滚动 705→16ms。
- **编辑会话的帧监听**：每个视频帧回调广播给所有视图的 `EditingView.observe`（111 次回调对应 330 次观察）。帧监听按视图注册，观察只在它读取的输入（编辑身份、就绪变化、键盘候选、配置）变化时运行，`matchMedia` 结果在模块级缓存。
- **开始屏幕**：挂载磁贴后同步读几何造成 139–147ms 的强制布局；改用 ResizeObserver 的尺寸并在尺寸不变时不更新状态，最长强制布局降到 53ms。

模糊（backdrop blur、resize 过渡）不是主线程成本：关闭后占用 935→932ms/s。Chrome 89 上三窗口动画（p95 50ms）和文件列表（66ms）仍略超目标，余下的是逐帧视频几何读取与行样式合成；窗口组切换、分屏拖动和开始屏幕打开仍有明显的挂载与布局成本。
