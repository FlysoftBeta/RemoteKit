# 文件、文件篮与拍照

网页的 `<input type=file>` 不弹出本地系统文件选择器，而是打开 Viewer 的文件篮：从设备选文件、拍照、或从"我的文件"里取。本文描述数据如何流动、各方保存什么、以及拍照和文档扫描的设计。

## 三个对象，分开管理

| 对象 | 所有者 | 内容 |
|---|---|---|
| 资产（asset） | 对象存储（Endpoint 节点上的加密对象，Control 的对象索引） | 不可变字节，id = 集群对象密钥对内容的 HMAC；所有 Tenant 共用一份并去重，可以有多个节点上的副本 |
| 目录条目（library entry） | Control SQLite | 名称、来源、分区、时间、是否已收集、照片元数据；引用资产 hash |
| 篮子与选择事务 | Control SQLite | 篮子顺序；一次原生选择的不可变清单与终态 |

同一个资产可以被多个条目引用，各条目有独立的名称、来源、分区和收集状态。资产 id 本身不授予访问：Session 只能读它的 Tenant 引用或认领的对象；没有集群对象密钥的一方也无法用内容 hash 推出 id。对象格式、副本与回收见[多节点 · 对象存储](cluster.md#对象存储)。

**数据路径**：文件字节和照片分析全部走已有的 WebRTC DataChannel（`files.request/result`，version 1），由 Session 拥有的有界磁盘线程处理；元数据走鉴权的 WebSocket。Control 只授权不透明的绑定，从不打开 Endpoint 的磁盘路径——Control 与 Endpoint 可以在不同机器上。哈希、拷贝、OpenCV 不持有媒体锁或 Browser 锁。

## 原生文件选择

网页文件选择必须完成 Chromium 真实的 `RunFileChooser` / `FileSelectListener`，这样页面激活、`File.name`、延迟读取、按文档取消都保持原生语义。脚本给 `input.files` 赋值不是产品集成方式。

1. Browser 的 `PageRequests` 保留原生 listener。Control 的 `fileRequests` 投影暴露不透明请求 ID、所属 Tab/Window、来源 origin、multiple/accept 提示、状态和限制。内部绑定包含 Tenant、Browser incarnation、view/instance/document/原生请求号。
2. accept 只是选择器提示，不是 MIME 安全门：最多 64 个提示、每个 256 UTF-8 字节、序列化后 16KiB；超出时标记 `acceptTypesOmitted`，Viewer 去掉本地 accept 限制。不支持目录上传。
3. 用户在篮子里确定选择后：`library.prepare`（Control 校验原生请求、multiple、数量、大小，写入不可变的选择清单）→ DC `selection.commit`（Endpoint 再校验当前 peer、授权和真实的待处理原生请求，把资产暂存为 Browser 可读的文件，回调 listener）→ `library.finish`。
4. 暂存：随机磁盘文件名，`NativeFileInfo.display_name` 带用户文件名，回复和错误从不泄露本地路径；Windows 私有绝对路径用扩展路径形式（含 UNC），随机 ID 用 32 位十六进制，避免叠加的 MAX_PATH 失败。能硬链接时复用物理内容，否则复制。
5. 回调之前先持久化"已提交"：之后传输丢失时结果是未知，而不是"可以安全重发"。已提交但没有匹配 Browser 回执的选择保持 unknown，不重放已认领的原生回调。只有原子上仍处于 pending 时，才能在选择器退役时取消。
6. selected 回执只证明文件交给了 `FileSelectListener`，不证明网站自己的上传完成。Browser 的异步文件校验检查原始 `WeakDocumentPtr`；取消会移除 pending 所有权，迟到的校验完成不能把文件选进另一个文档。

**选择器锚点**：可见的主 frame 文件输入框有可靠位置时，文件篮锚定在它旁边（按输入框实际 bounds 与文档/布局身份，不按最后一次点击位置，见 patch 0016）；隐藏、移动、无效时撤销锚点；子 frame 中的输入框没有锚点，文件篮停在底部居中。浮层不会让远端页面 resize。

锚点的单位：Renderer 报告的 bounds 与 viewport 已是页面 DIP，但它附带的缩放是虚拟 Screen 的原始缩放（恒为 1），页面缩放由 Blink 设备模拟施加，所以 Browser 不用它，改报布局的页面 DSF（设备 DPR × 界面缩放）。客户端把视频画面的视觉 rect 换成布局 px 再与 DIP 尺寸核对，投影仍按视觉 px 计算，放置常量按界面缩放换算。

## 文件库

- 篮子最多 64 个唯一条目，目录最多 4096 条。收集状态与篮子成员身份独立：从我的文件直接导入立即收集；临时导入到篮子的文件只在原生选择确认后按来源规则收集或整理（见[工作区 · 我的文件](workspace.md#我的文件)）；从篮子移除不删除已收集文件。
- `library.import/replace/basket/group/move/delete/prepare` 都带操作 ID 并保存冻结的 payload 回执。`library.basket` 与 `library.replace` 先检查幂等重放，再做 `expectedRevision` CAS：过期的拖放不能重新插入已被消费的文件，也不能丢掉并发的导入。
- `library.finish` 在 Endpoint 持久化匹配 `selection_id` 的终态之后，原子地归档并从篮子移除精确的已选条目，仅一次。取消和未知不消费篮子。
- 引用与回收由 Control 的对象索引负责：目录条目、未决候选与未决选择引用资产，缩略图随源对象一起被引用；无引用超过 2 小时的对象从所有副本删除。显式删除需确认，被未决原生选择持有的条目拒绝删除。
- 预算：每 Tenant 对象字节配额由 Control 配置（`quotas.tenantObjectBytes`，默认 4GiB）按索引计算；Endpoint 只限制单文件 256MiB、草稿字节 512MiB、1024 个草稿、32 个活动草稿，草稿 30 分钟过期。上传 seal 时写入对象并向 Control `object.committed`，登记成功才算 seal 成功。给 Browser 暂存、生成缩略图或 Viewer 下载时本地没有该对象，就从持有副本的节点拉取。原生暂存另有自己的逻辑预算（单文件 256MiB，单批 512MiB/64 个文件，每 Session 1GiB/4096 个文件；零字节文件也占文件数预算），已选或可能已提交的数据计费到所属 Browser incarnation 确认退出为止。两个 1GiB 逻辑预算不等于总磁盘上限。
- 重启扫描只检查已识别的自有目录，不跟随 reparse/符号链接，按 max(声明的预留, 实际大小) 计费；预留无效或缺失、访问失败、扫描溢出时保守地把配额置满。未知目录和归属未确认的旧文件不是可删除的缓存。
- 上传：`asset.begin/chunk/seal/cancel`，每块最多 16384 字节（base64 编码后），最多 4 块在途，DataChannel `bufferedAmount` 有界；Endpoint 只在实际写入后确认 offset；同 offset 相同字节可幂等重放，错误 offset/数据不行。篮子的库授权使用 `requestId='library'`，与原生选择器的授权分开；锁定、peer 变化、授权代次变化同时撤销两者。
- 缩略图：内容寻址的 JPEG，最长边 320、最大 64KiB，最多 256 个源映射；客户端按可见性懒加载，带有界缓存（96 项、2MiB、128 个待处理订阅，失败冷却 30 秒）。WIC 在完整 RGB 分配前先缩小 JPEG/PNG，输入上限 64MiB 压缩、32Mi 像素、单轴 16384；不支持的格式显示文件图标。
- 文件库元数据有自己的每 Tenant 队列，重连后通过 `library.get` 对账；客户端不持久化目录。

**界面**：只有文件篮和相机两个主界面。

- 文件篮是非模态悬浮面板：没有遮罩，不遮挡下方操作，点页面不会关闭它；顶部 handle（整个标题栏）可拖动，拖过之后不再跟随锚点，保持至少 64px 在可视区内。标题栏不放文案，只有拖动 handle 和关闭按钮（规则由发送按钮的提示说明）；只有关闭按钮或"更多"里的取消会取消选择，Escape 只收起内联步骤。
- 图片为主时用横向卡片：整卡拖拽、点击打开菜单（查看大图、照片详情、重拍、在后面插入、移除），需要决定的照片（待选片、扫描未完成、失败、处理中）直接展开内联面板；触摸横扫浏览、长按 200ms 开始排序；简易形态是小卡片条（96×124）和右侧纵向的发送/添加/更多图标（44px），发送是填充的主色圆钮，多选时角标显示数量。至少 3 个普通文件且占三分之二以上时默认用列表：手柄拖拽，操作直接展开为图标按钮；可以在"更多"里切换视图（只对当前组件实例有效）。拖拽预览只在本地，放下时用捕获的 revision 提交一次；取消、断线或权威集合变化时放弃。
- "添加"是菜单：从设备选择、摄像头拍照、从我的文件选择；从卡片的"在后面插入"进入时插到该项之后。从我的文件选择是多选网格（可按文件名过滤），按点选顺序一次加入。空篮直接显示这三个入口；可以把桌面文件拖进文件篮。
- multiple 时发送整个篮子的顺序（有未决项时阻止）；单选需要用卡片角上的单选框明确选中一项。
- 我的文件是独立的 App（见[工作区 · 我的文件](workspace.md#我的文件)），按日期分节、时间倒序，可按文件名搜索，卡片/列表两种视图；点文件打开菜单（查看、照片详情、加入或移出文件篮、移到分区、选择多个、删除），列表行直接带加入文件篮开关。选择模式（悬停复选框、触摸长按或"选择"）下可批量加入文件篮、移动、删除。上传菜单有从设备选择与拍照，也可把文件拖进窗口；在分区视图中上传直接进入该分区。文件篮的更多菜单可选"发送后整理到"分区。
- 文件卡片与行共用 `FileTile`/`FileRow`：图片缩略图裁切填满，其他文件按类型（PDF、文档、表格、演示、压缩包、音视频、文本）显示着色图标和扩展名；大小用 B/KB/MB。

## 文档预览

我的文件和学习 App 用同一个阅读器预览文档：PDF、Word/WPS 文字、PowerPoint/WPS 演示、Excel/WPS 表格、OpenDocument、RTF 与纯文本。图片用图片预览，音视频用浏览器原生播放器，其他类型显示文件卡片。

**转换**（Endpoint，`endpoint/src/documents/`）：非 PDF 先用无界面的 LibreOffice 转成 PDF，再用 pdfrender（FlysoftBeta/pdf-render，poppler 的派生）渲染成 `classapp-render-archive` v2 归档：每页是绝对定位的可选择 HTML 文字层叠在 Cairo SVG 背景上，图片转为 WebP，文本资源各自 zstd 压缩（可带字典），整个归档是只用 STORED 的 ZIP64，可按偏移直接读。选 LibreOffice 是因为节点上没有、也不能假设有 MS Office，而它对 Office 与 WPS 格式的保真度在可部署的方案里最好；pdfrender 的输出在 Chrome 89 上也能还原排版、保留文字选择。

- 每个节点一个渲染队列：最多 2 个并发，队列 64，同一源对象的并发请求合并为一次。LibreOffice 与 pdfrender 各自运行在 Job Object 里（关闭即杀、内存 2GiB、无窗口），超时 180 秒；LibreOffice 使用 Endpoint 数据目录下 2 个常驻的用户配置（不按任务新建，热启动的 DOCX 约 7 秒，冷启动约 30 秒），输入先复制到私有临时目录并改成 ASCII 文件名。PDF 渲染通常不到 0.1 秒。
- 结果是一个以源对象为 `derivedFrom`、`kind: 'document'` 的派生对象，随源对象一起被引用和回收；因为对象存储跨 Tenant 去重，同一份课件全集群只转换一次。转换失败按源对象缓存 10 分钟，加密、损坏、超时给出简短原因。
- 学习 App 下载附件后由 Control 请求预渲染（`object.render{id}`，交给持有副本的节点），用户打开时通常已经就绪。Control 是学习附件转换的唯一发起者：同一源对象在全集群同时只有一个转换；结果记在 `object_render_failures`——确定性失败（损坏、加密、不支持）不再自动重试，任何 Tenant 的同步都不会再次转换它；暂时性失败（unavailable、busy、超时）按 1、2、4、8、16 小时退避，最长 24 小时；结果未知时只在原节点重试（它的队列按源对象合并）。源对象删除或派生完成时清掉记录。
- Viewer 打开这类源对象时，Endpoint 向 Control 查询派生对象；Control 的转换仍在进行时回复 `busy`，Endpoint 把它作为 `{state:'converting'}` 交给 Viewer 继续轮询，而不是在本节点再转换一次；本节点渲染队列已满（`busy`）同样报告为 converting。
- 转换失败的 Endpoint 日志写明工具（soffice / pdfrender）、退出码与 stderr 最后几行（去掉路径与文件名），不写文件内容。

**读取**：归档的 ZIP、zstd 与 hash 校验都在 Endpoint 完成，Viewer 只拿解码后的资源。DataChannel 文件服务（与 `asset.read` 同样的库授权）提供：

- `document.open{assetId}` → `{state:'ready', documentId, pages:[{id, ordinal, width, height, document, dependencies}], shared}`、`{state:'converting'}`（Viewer 每 1.5 秒再问，最多 5 分钟）或错误（`invalid_request` 不是文档，`rejected` 转换失败）。
- `document.resource{documentId, contentId, offset}` → 与 `asset.read` 相同的分块回复并带 `mime`；Endpoint 每节点保持 8 个打开的归档。

**阅读器**（`control/client/documents/`，取自 talos-ng 的阅读器与虚拟滚动）：页面虚拟化，只挂载视口附近的页并按需取资源，资源 Blob URL 有界 LRU（64 项、32MiB）；每页挂在自己的 shadow root 里，内联样式表，`data-bundle-ref` 解析为 Blob URL，其他 URL 一律去掉，页面内容不会发出网络请求；按 pdfrender 约定给多字符单词设置 `--fit-x` 对齐原始字宽。默认适应宽度，可缩放（按钮、双指、Ctrl+滚轮）。页面控制是浮在页面上方、底边居中的胶囊：页码（点开直接跳页）、缩小、缩放比例（点按回到适合宽度）、放大；内容底部留出空间让最后一页能滚出胶囊；精确指针设备上 2.5 秒无操作淡到 35%，指针移动或滚动时恢复，触屏设备上保持不透明。打开中显示文件类型图标、名称与进度条；Endpoint 报告转换中时改为"正在转换文档"，20 秒后加一行"仍在转换…"；转换失败显示"无法转换此文档"与原因、重试。阅读位置（页号与页内偏移）存在 Control（见[学习与题库 · 文档阅读进度](learning.md#文档阅读进度)）。

**依赖**：`tools/fetch-document-deps.py` 按固定版本与 SHA-256 获取 LibreOffice MSI（管理安装解包，不改系统）与 pdfrender Windows 构建（GitHub Actions 产物，过期前需要刷新固定值），按确定的允许/拒绝清单裁掉词典、界面翻译、帮助、模板、Python/Java 等转换用不到的部分（约 460MiB，裁剪前后转换结果逐像素一致），开发构建复制到 `endpoint_service.exe` 旁的 `documents/`，Endpoint 运行时包里同样位置，附带两者的许可证。

## 拍照

拍照用浏览器摄像头（getUserMedia）在本地取帧，与远端页面的 H.264 和 Viewer 串流完全无关。设计目标：快门之后尽快可以继续拍；选出的是"足够好"的那一帧；原图不经过任何视频编解码。

**取景与快门**：全屏 cover 预览。输出取预览实际可见的那块源矩形：`s = max(viewW/srcW, viewH/srcH)`，裁剪 `(viewW/s, viewH/s)`，在源中居中。快门冻结裁剪、方向和模式；从不放大源像素；上限 8Mi 像素；理想请求 3840×2160@30，以实际设置为准。横屏快门在右侧中间，竖屏在底部中间；控件浮在预览上；连续拍摄默认开启；模式与连续拍摄在相机内选择。

**采样**：一次快门最多 1 秒、最多 20 个**不同的**源帧，按绝对 50ms 时隙取样（用 rVFC 帧元数据，或保守的可用帧回退）。每个采样同时冻结一份原图快照，并从**同一份**像素生成分析用 JPEG（最长边 512，≤44KiB，质量依次尝试 .8/.6/.4/.2）。同时只有一个分析请求在途；时隙忙或内存不足时跳过该时隙，不复制帧，也不延长快门时间。原图池最多两个保留候选加一个当前快照。

**选帧（Endpoint）**：`photo.burst.begin/sample/end/cancel`。Endpoint 评估区域细节、过曝/欠曝裁剪、平坦区噪声、亮度/色度签名（判断近重复）。两个近重复样本得分都 ≥0.60 且没有接近的竞争者时提前停止；得分低于 0.26 给出警告；得分差 ≤0.095 且内容不同时保留两个候选。Endpoint 只能从客户端仍持有的 `availableFrameIds` 中选；end/cancel/撤销之后迟到的样本结果不能重启采集；重放的 ID 或已丢弃的快照被拒绝。每 Session 最多 2 个活动 burst、每个 20 个样本、5 秒寿命；32 个 end 结果回执保留 30 秒用于精确重放。

**之后**：只有选中的原图（以及确实不确定时的另一个候选）被编码为无损 PNG 上传；分析 JPEG 从不当作原图保存。采样结束即释放快门，PNG 编码、上传、扫描处理在后台进行：后台任务最多 2 个，加 1 个当前采样，每个任务编码字节预算 72MiB；任务按快门顺序入篮；离开相机不销毁已采样的工作；认证或身份丢失时取消。拍完直接入篮，没有独立的"检查照片"页；只有不确定时篮子里才出现候选供选择、移除或原位重拍。重拍保留旧条目直到替换就绪，`library.replace` 保持条目 ID、顺序、文件名、时间、分组和归档状态。未决的照片不能用于原生选择。

**被否决的设计**：

- 旧流程串行拍 6 张完整 JPEG、编码、上传、再打分：在 10ms RTT 下 16KiB 停等每 MiB 至少 640ms，还没算处理时间。
- `takePhoto()` 用来"定稿"一个已经打过分的预览帧：它可能触发新的曝光、不同的裁剪和分辨率，在一些设备上还会打断预览。
- 原始 RGB 以 20fps 上传做分析：768×432 RGB 约 159Mbps。
- 主线程绘制+读回+灰度在首个快照就要 31ms；后来的 Worker 打分方案连同其工具已退役，打分现在在 Endpoint。
- 用户否定的布局：contain 预览（取景被挤小）、横屏底部快门（难触达）、三段式流程（拍→检查→保存）。

## 文档扫描

`ProcessPhoto` 保持输入资产不变，写出新的 PNG 衍生资产。扫描只有一个用户模式，内部有三种几何结果：

1. **透视矫正**：有可信的完整页面证据时——显式给出的顺时针归一化四角，或者通过凸性、边缘支撑、歧义检查的完整四边形。画面边框、表格内线、阴影、推断出的画外第四条边都不足以裁掉已拍到的内容。
2. **纠斜**：文本方向一致时。在 512 尺度上对暗色连通域做 ±15°、0.5° 步长的投影，要求空间/行支撑以及水平子区域之间的一致；接受的小角度旋转会扩展画布以容纳所有变换后的角点。对齐、稀疏、混排、弯曲或有歧义的文本保持原几何。
3. **保持原几何**，然后做增强。

增强：小尺度灰度形态学估计光照，三个颜色通道共享一个有节制的亮度增益，保留高光余量，限制暗块与边缘的放大。不做黑白硬二值化，保留印章、彩色文字和浅色笔迹；几何不确定是正常结果，不是失败。

限制：8Mi 像素、最长边 8192、压缩输入/输出 PNG 64MiB；分配前检查，长时间的行/阶段循环检查取消。扫描失败在篮子里明确显示：用户重试或明确使用原图，从不把未处理的图标记为已扫描。

被否决：旧方案要求检测到完整页边、并把 RGB 转灰度后按 0.95 局部比例贴白——不完整入镜的页面直接失败，浅色字迹和颜色消失。UVDoc 去扭曲模型改善了合成样例的行弧，但会删掉已入镜的边缘内容（不完整页面样例中的边缘标记从 8 个降到 0–1 个），并且在 OpenCV 推理中遇到动态 Shape、GridSample、5D reflect Pad 等障碍；为一个已经不满足"不丢内容"要求的模型引入 ONNX Runtime 和数百 MiB 内存不合算。书脊非线性展平和 OCR 未实现；硬阴影或深色边界可能有窄光晕。
